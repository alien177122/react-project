# Промт: разбор видео про инструменты (для Claude / ассистента)

Переиспользуемый шаблон для разбора видео/рилсов/статей про dev/design/AI-инструменты. На выходе — карточки с рисками под конкретный стек, алгоритмы внедрения, привязанные к реальным файлам репо, приоритеты с определёнными осями и фиксация решения в Memory Bank.

**Версия:** 2.0 (исправлена после провального прогона v1 — см. раздел «Changelog»)

---

## Как использовать

1. Открой Claude (или иного ассистента, у которого есть доступ к репо).
2. Скопируй блок **«Промт v2»** целиком (от кода ```text ... ```).
3. Вставь транскрипт/конспект/ссылку на видео вместо `[транскрипт / конспект / ссылка на видео]`.
4. Для глубокого разбора одного инструмента добавь в конец промта строку из раздела **«Опциональные модификаторы»**.
5. Сохрани результат ассистента, если он полезен — в `memory-bank/techContext.md` (заметка) или создай задачу в `memory-bank/tasks.md`.

> Контекстный блок промта уже зашит под стек этого монорепо (Capacitor 7 / Vite / React 19 + Expo Router + react-native-macos). При переносе в другой проект — обнови блок «КЛЮЧЕВОЕ О СТЕКЕ».

## Промт v2

```text
Действуй как инженер-аналитик и продуктовый технолог. Я даю тебе [транскрипт / конспект / ссылка на видео]. Разбери упомянутые инструменты по схеме ниже.

ШАГ 0 — ПЕРЕД ОТВЕТОМ прочитай репозиторий и держи в уме (не переспрашивай того, что есть в файлах):
- package.json (корневой), apps/mobile/package.json, apps/macos/package.json, capacitor.config.ts
- memory-bank/activeContext.md, memory-bank/tasks.md, memory-bank/techContext.md, AGENTS.md
Цель — понять реальный стек, активные задачи и боли. Если чего-то критичного правда нет в репо — задай ОДИН уточняющий вопрос в самом начале и остановись.

КЛЮЧЕВОЕ О СТЕКЕ (сверяй с package.json, не полагайся на память):
- Двойной трек (боль): ОСНОВНОЙ — веб на Vite + React 19, обёрнутый Capacitor 7 в натив iOS/Android; ВТОРИЧНЫЙ — Expo Router (apps/mobile/, SDK 54 / RN 0.81.5 / React 19); ДЕСКТОП — react-native-macos (RN 0.76 / React 18). Бизнес-логика в packages/shared, strict TS, без any.
- Сеть: на устройстве/эмуляторе относительные /api не работают — нужен абсолютный VITE_API_URL на сборке.
- Воркфлоу: Memory Bank (activeContext/progress/tasks/reference); компоненты ≤150 строк; логика в хуках/utils.
- ПРОВЕРКИ: react-doctor ТОЛЬКО для React/RN/Expo кода — НИКОГДА не применять к документам, markdown, выводу MarkItDown, конфигам.

ПРАВИЛА:
1. Не выдумывай ссылки, версии, лицензии, факты. Не уверен — пиши «требует проверки». Каждую ссылку отдельной строкой: `Название — url` (проверь, что это канонический источник, а не зеркало).
2. Русский. Кратко, без воды, без эмодзи, без восклицаний.
3. Источник видео — соцсеть/рил → часто маркетинг. Помечай хайп, недоказанные утверждения, vendor lock-in.
4. Перед рекомендацией проверь: нет ли в проекте УЖЕ решающего эту задачу (в т.ч. в текущих MCP-серверах и devDeps). Если есть — сравни, нужен ли второй.

ФОРМАТ ОТВЕТА:

1. РЕЗЮМЕ ВИДЕО (2–4 строки): о чём, для кого, главная ценность. Тон: инженерное обоснование / маркетинг / смешано.

2. КАРТОЧКИ ИНСТРУМЕНТОВ — по каждому упомянутому:
   • Название + категория (библиотека / сервис / dev-tool / CLI / AI-workflow / дизайн / протокол).
   • Класс риска: DEV-TOOL (нет влияния на рантайм/бандл) / RUNTIME (зависимость в сборку) / INFRA (CI, MCP, конфиг).
   • Канонические ссылки: docs и/или repo (или «найти вручную»).
   • Что это — 1–2 строки.
   • Какую проблему решает.
   • Дублирование: есть ли в проекте аналог (назвать файл/пакет/MCP). Нужен ли второй — да/нет/почему.
   • В МОЁМ проекте: где применимо (экран/фича/утилита из репо), ожидаемая польза, риски под МОЙ стек (новая архитектура RN, Expo config-plugin, Capacitor-плагин, Vite vs Metro, Hermes, размер бандла под macOS, strict TS, a11y). Неприменимо — скажи прямо.
   • За пределами проекта: где ещё полезен.
   • Чек-лист совместимости (только для класса RUNTIME): RN New Arch / Expo-совместимость / Capacitor / Hermes / bundle / лицензия / активность репо.
   • Алгоритм внедрения — пошагово, ПРИВЯЗАННЫЙ к реальным файлам/командам/версиям моего репо (не «install → restart»): где ставим (root/apps/mobile/apps/macos), какой конфиг правим, в какую фичу интегрируем, как проверяем, как откатываем. Уместно — мини-сниппет.
   • Kill criteria — когда НЕ внедрять (порог отказа: цена поддержки, lock-in, дублирование, нестабильность).
   • Альтернативы (1–2) и когда выбрать другой.

3. ПРИОРИТЕЗАЦИЯ — таблица с ЯВНО определёнными осями:
   Ось Польза 1–5: 5=решает активную боль из контекста (назвать какую) / 4=ускоряет фичу в плане / 3=удобство, не блокер / 2=маргинально / 1=не применимо.
   Ось Усилия 1–5: установка+интеграция+поддержка; 5=>1 дня+новые зависимости+риск+постоянная поддержка … 1=одна команда, изолированно, zero maintenance.
   Колонки: Инструмент | Класс | Польза | Усилия | Рекомендация (сейчас/позже/нет) | Одно объяснение «почему так».

4. POC-ЭКСПЕРИМЕНТ для топ-1 инструмента: конкретный мини-тест с измеримым критерием успеха (что докажет ценность за 30–60 минут).

5. ПЕРВЫЕ 3 ДЕЙСТВИЯ НА СЕГОДНЯ — что запустить/поставить/прочитать, со ссылкой на конкретный файл репо.

6. MEMORY BANK: куда записать решение (tasks.md как задача / techContext.md как заметка о工具) и формулировка одной строкой.

7. ЧТО ПРОВЕРИТЬ ДО РЕШЕНИЯ — доки/issue/бенчмарки/лицензия.
```

## Опциональные модификаторы

Добавь одну из этих строк в **конец** промта под нужный режим:

**Глубокий разбор одного инструмента** (вместо беглого обзора всех):
```
Сосредоточься на одном инструменте — [название]. Игнорируй остальные. Дай расширенный алгоритм внедрения с примерами кода под мой стек, расширенный kill-criteria и конкретный план отката.
```

**Видео на английском** (ответ всё равно на русском):
```
Транскрипт на английском — ответ всё равно на русском, термины оставляй на языке оригинала (Expo config plugin, New Architecture и т.п.).
```

**Только компактная выжимка** (для быстрых рилов, без глубокого разбора):
```
Компактный режим: только резюме видео + таблица приоритетов + 3 действия. Пропусти карточки с расширенным алгоритмом внедрения.
```

## Настройка под другой проект

Если используешь промт вне этого монорепо — замени блок **«КЛЮЧЕВОЕ О СТЕКЕ»** (между `КЛЮЧЕВОЕ О СТЕКЕ` и `ПРАВИЛА:`). Шаблон для нового контекста:

```text
КЛЮЧЕВОЕ О СТЕКЕ (сверяй с package.json, не полагайся на память):
- Основной стек: [фреймворк + версия, рантайм, тип сборки].
- Платформы/таргеты: [web / iOS / Android / desktop / server].
- Логика: [где лежит бизнес-логика, state-менеджмент, строгий TS или нет].
- Сеть/интеграции: [особенности — относительные пути не работают / OAuth / etc].
- Воркфлоу: [Memory Bank? компоненты ≤N строк? отдельные хуки/utils?].
- ПРОВЕРКИ: react-doctor ТОЛЬКО для React/RN/Expo кода — НИКОГДА не применять к документам, markdown, выводу MarkItDown, конфигам.
```

## Changelog

### v2.0 — что исправлено после провального прогона v1

Прогон v1 дал: общие алгоритмы (install → restart), применение `react-doctor` к markdown-документу (бессмыслица), повторное рекомендование MCP без учёта уже стоящих `playwright` + `sqlite` MCP, произвольные числа в шкале приоритетов и финальный переспрос версии Expo, хотя репо был доступен.

Закрытые провалы:

| # | Провал v1 | Что добавлено в v2 |
|---|-----------|--------------------|
| 1 | Неточный контекст: промт говорил «RN + Expo», хотя стек гибрид Capacitor + Expo + react-native-macos | Контекстный блок переписан под реальный двойной трек с версиями |
| 2 | В конце модель всё равно переспрашивала версию Expo, не читая репо | **Шаг 0**: «прочитай репо» перед ответом; переспрос только если критичного нет в файлах |
| 3 | `react-doctor` применили к выводу MarkItDown (markdown) | Явное ограничение: react-doctor — только для React/RN/Expo кода |
| 4 | Алгоритм внедрения был общим (install → config → restart → test) | Алгоритм должен быть привязан к конкретным файлам/командам/версиям репо |
| 5 | Не было проверки на дублирование с уже стоящими инструментами | Поле «Дублирование» в каждой карточке (назвать файл/пакет/MCP) |
| 6 | Шкала приоритетов без определения осей → числа произвольные | Оси Польза и Усилия определены явно + колонка «почему так» |
| 7 | Нет фильтра «маркетинг vs инженерия» (источник — инста-рил) | Правило 3: помечать хайп, недоказанные утверждения, lock-in |
| 8 | Все инструменты в одной корзине риска | Класс риска: DEV-TOOL / RUNTIME / INFRA + отдельный чек-лист совместимости для RUNTIME |
| 9 | Нет связи с Memory Bank | Блок 6: куда записать решение (tasks.md / techContext.md) |
| 10 | Нет критерия отказа | Поле «Kill criteria» в каждой карточке |

### v1.0
- Базовый промт: резюме, карточки, приоритизация, первые действия, что проверить. Контекст был общим (RN + Expo, shared-пакет).
